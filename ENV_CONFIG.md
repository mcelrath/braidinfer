# User-Facing Environment Variables

This file documents the **current** environment-variable interface that the
`generate`, `chat`, and `braid_bench` binaries expose. It is an anti-pattern.
The desired end state is proper CLI arguments (clap) for runtime knobs and a
TOML/JSON config file for model-specific defaults; these env vars exist
because each one was bolted on during a specific investigation and never
graduated.

Companion files:

- `DIAGNOSTICS.md` — `BRAIDINFER_*` diagnostic / probe / kernel-tuning env
  vars (not user-facing).
- `MODELS.md` — model matrix (which `.bqnt` for which architecture).
- `CLAUDE.md` — project root docs, including the mandatory
  `scripts/launch-gpu.py` invocation convention used in the examples below.

All examples wrap the command in `scripts/launch-gpu.py` per `CLAUDE.md`.
Env vars are set **before** the `python3` invocation; they are inherited by
the wrapped `cargo` / `target/release/...` process.

## `MODEL`

**What.** Selects the model to load. Accepts either a HuggingFace snapshot
directory (containing `config.json` + `tokenizer.json`) or a `.bqnt` file
path. When a `.bqnt` is given, the matching HF snapshot is auto-resolved from
`~/.cache/huggingface/hub` using the `model_name` metadata inside the bqnt,
and `BQNT_PATH` is set in the process environment for downstream code. If
unset, `cli::DEFAULT_MODEL_DIR` (Qwen3.5-0.8B snapshot) is used.

**Usage.**
```bash
MODEL=/path/to/qwen35_2b.q4.bqnt MAX_TOKENS=64 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** String path. Default = Qwen3.5-0.8B HF snapshot path
hard-coded in `crates/braidinfer-runtime/src/cli.rs:12`.

**Why created.** Origin not recoverable from transcript as a discrete event;
it is the primordial knob for `generate`/`chat` and predates the diagnostic
sprawl. Required because the runtime has no CLI parser yet.

**Where read.**
- `crates/braidinfer-runtime/src/bin/generate.rs:24`
- `crates/braidinfer-runtime/src/bin/chat.rs:22`
- `crates/braidinfer-runtime/src/bin/op_profile_dump.rs:23`
- `crates/braidinfer-runtime/src/bin/sew_diag.rs:13`
- `crates/braidinfer-runtime/src/bin/braid_bench.rs:602`

**Migration note.** Would become `--model <path>` positional/required CLI
arg, with a `[default]` block in a config file naming the fallback snapshot.

## `BQNT_PATH`

**What.** Explicit path to a `.bqnt` pre-quantized weight file. Takes
priority over the auto-derived `<model_dir>/<name>.q4.bqnt`. When `MODEL` is
itself a `.bqnt`, `resolve_model_arg` writes that path back into
`BQNT_PATH` via `std::env::set_var` so the loader sees it. If unset and no
bqnt exists alongside the safetensors, the loader will create one on first
quantization run (only when `WEIGHT_QUANT != Bf16`).

**Usage.**
```bash
MODEL=/home/.../Qwen--Qwen3.5-0.8B/snapshots/<sha>/ \
BQNT_PATH=/path/to/custom.q4.bqnt \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** String path. Default = auto-derived sibling
`<model_dir>/<basename>.q4.bqnt`, or none.

**Why created.** Decouples the HF snapshot dir (config + tokenizer) from
the pre-quantized weight blob. The transcript shows the user routinely
points `BQNT_PATH` at custom-quantization output files generated by
`quant_save` / `bisect_quant.py` workflows so the same HF snapshot can be
loaded against multiple quantization variants without copying files into
the HF cache tree.

**Where read.**
- `crates/braidinfer-runtime/src/cli.rs:99,141`
- `crates/braidinfer-runtime/src/model/model_load.rs:60,1192`
- `crates/braidinfer-runtime/src/bin/braid_bench.rs:612,636`

**Migration note.** Would become `--bqnt <path>` CLI arg; auto-derivation
stays as the default resolver.

## `MAX_TOKENS`

**What.** Decode-step budget. `generate` stops after this many new tokens
even if no stop token is hit; `chat` uses it as the per-turn budget.

**Usage.**
```bash
MODEL=$MODEL MAX_TOKENS=20 \
  python3 scripts/launch-gpu.py --timeout 600 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Write a haiku"
```

**Default / values.** Unsigned integer. Default = 64 in `generate`, 4096
in `chat`, 1 in `op_profile_dump`.

**Why created.** Origin not recoverable as a discrete event. The
transcript shows `MAX_TOKENS=1` used heavily as the canonical
trace-comparison setting for kernel-change validation (see
`CLAUDE.md`'s activation-trace requirement) and `MAX_TOKENS=20`/`64` for
quick smoke tests.

**Where read.**
- `crates/braidinfer-runtime/src/bin/generate.rs:17`
- `crates/braidinfer-runtime/src/bin/chat.rs:15`
- `crates/braidinfer-runtime/src/bin/op_profile_dump.rs:26`

**Migration note.** Would become `--max-tokens N` CLI arg.

## `MAX_SEQ_LEN`

**What.** Caps the model's `max_seq_len` at load time, overriding the
config value and the runtime's `DEFAULT_MAX_SEQ_LEN` ceiling. Reducing it
reduces KV-cache VRAM allocation linearly with context length.

**Usage.**
```bash
MODEL=$MODEL MAX_SEQ_LEN=512 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** Unsigned integer. Default = `min(config.max_seq_len,
Model::DEFAULT_MAX_SEQ_LEN)`.

**Why created.** Origin not recoverable as a discrete event. Used in the
transcript with values `128`/`256`/`512` to fit large MoE / 70B-class
models into a single GPU's VRAM budget for prefill/decode benchmarks
without paying for a 32K-token KV reservation.

**Where read.**
- `crates/braidinfer-runtime/src/bin/generate.rs:30`
- `crates/braidinfer-runtime/src/bin/chat.rs:40`
- `crates/braidinfer-runtime/src/bin/braid_bench.rs:52`
- consumed in `model_load.rs:40`

**Migration note.** Would become `--max-seq-len N` CLI arg, with the
config-file ceiling as a separate `model.max_context_tokens` field.

## `RAW`

**What.** Switches `generate` from chat-template mode (`chat_generate`,
which wraps the prompt in the model's chat template) to raw greedy
continuation (`greedy_generate`, prompt is tokenized as-is). Only affects
the `generate` binary; `chat` is always chat-template.

**Usage.**
```bash
RAW=1 MODEL=$MODEL MAX_TOKENS=1 TRACE=ref.bin \
  python3 scripts/launch-gpu.py --timeout 300 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** Presence flag (set to anything = on). Default = off
(chat-template wrapping).

**Why created.** Origin not recoverable as a discrete event, but the
transcript shows `RAW=1` as the standard mode for activation-trace
comparison — the chat template injects role tokens that differ between
model variants and break per-token trace diffs. `CLAUDE.md`'s trace
example uses `RAW=1`.

**Where read.** `crates/braidinfer-runtime/src/bin/generate.rs:22`.

**Migration note.** Would become `--raw` boolean flag on the `generate`
subcommand (mutually exclusive with chat template).

## `THINK`

**What.** Enables the chat-template `enable_thinking=true` variable for
Qwen3-family models that have a `<think>...</think>` block in their
template. `chat` then renders the thinking text dimmed on stderr so the
assistant's visible answer stays clean on stdout.

**Usage.**
```bash
MODEL=$MODEL THINK=1 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin chat
```

**Default / values.** Presence flag. Default = off.

**Why created.** Origin not recoverable from transcript as a discrete
event; added to expose Qwen3's thinking mode, which the chat template
gates on a Jinja variable rather than a separate template.

**Where read.** `crates/braidinfer-runtime/src/bin/chat.rs:70`; the value
threads into `apply_chat_template_thinking`.

**Migration note.** Would become `--think` CLI flag on the `chat`
subcommand.

## `MULTI_GPU`

**What.** Enables multi-GPU tensor/expert parallelism. The runtime shards
weights across all visible GPUs and uses P2P paths for cross-GPU
activations. If unset, `apply_auto_modes` auto-enables it when the bqnt
file size exceeds 85% of a single GPU's free VRAM and more than one GPU
is visible.

**Usage.**
```bash
MODEL=$MODEL MULTI_GPU=1 \
  python3 scripts/launch-gpu.py -g 4 --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** Presence flag (`MULTI_GPU=1`). Default = auto
(see above).

**Why created.** The user-facing entry point for the multi-GPU code path
that has dominated recent investigations (`braidinfer-snl` MoE-wedge,
`braidinfer-zqw` merge, the §11.4 cross-GPU visibility race). Auto-mode
was added so users with large MoE models don't have to remember the flag.

**Where read.**
- `crates/braidinfer-runtime/src/cli.rs:168,172` (auto-mode)
- `crates/braidinfer-runtime/src/model/model_load.rs:54`
- `crates/braidinfer-runtime/src/bin/braid_bench.rs:550,653,655`

**Migration note.** Would become `--multi-gpu` / `--single-gpu` CLI
flags, with the auto-detection threshold (`0.85`) moving to a config
field `runtime.multi_gpu_vram_threshold`.

## `PERSISTENT`

**What.** Enables the persistent cooperative `persistent_worker`
megakernel for decode (vs. the per-step kbk dispatch path). Auto-enabled
for any multi-GPU run and for any non-MoE single-GPU model (2.1×
speedup); auto-disabled for single-GPU MoE until the MoE path is
validated on the persistent worker.

**Usage.**
```bash
MODEL=$MODEL PERSISTENT=1 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

Force-disable an auto-enabled persistent path (rare, debug only):
```bash
PERSISTENT=0 MODEL=$MODEL \
  python3 scripts/launch-gpu.py --timeout 43200 -- cargo run ...
```
(Note: the code checks `PERSISTENT == "1"` strictly; `PERSISTENT=0` only
suppresses the auto-enable banner — see `apply_auto_modes`.)

**Default / values.** `"1"` to enable. Default = auto (`true` for
multi-GPU or non-MoE single-GPU).

**Why created.** Exposes the persistent cooperative megakernel
(`kernels/megakernel.hip` → `persistent_worker` entry, described in
`CLAUDE.md` "Megakernel" section). The auto-rule was added because the
persistent worker is required for the multi-GPU MoE dispatch path
(remote workers depend on the mailbox) and beneficial enough on dense
single-GPU models (2.1× speedup) that users shouldn't have to opt in.

**Where read.**
- `crates/braidinfer-runtime/src/cli.rs:185,186` (auto)
- `crates/braidinfer-runtime/src/model/model_load.rs:1117`
- `crates/braidinfer-runtime/src/bin/braid_bench.rs:664,665`

**Migration note.** Would become `--persistent` / `--no-persistent` CLI
flags; the auto-rule moves to `runtime.persistent.auto = "moe-aware"` in
the config file.

## `KV_QUANT`

**What.** Enables int4 residual-per-channel quantization of the KV cache
(in addition to whatever weight quantization is active). Reduces KV VRAM
~4× at decode but requires the paged KV path; the code rejects the
combination `KV_QUANT=1 MULTI_GPU=1` and `KV_QUANT=1 PERSISTENT=1` as
unsupported.

**Usage.**
```bash
MODEL=$MODEL KV_QUANT=1 MAX_SEQ_LEN=4096 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin chat
```

**Default / values.** `"1"` to enable. Default = off.

**Why created.** Memory-footprint relief for long contexts on
single-GPU. The transcript shows the explicit guard text "KV_QUANT=1
with PERSISTENT=1 is not yet supported. Either unset KV_QUANT or unset
PERSISTENT." — i.e. it was added as a single-GPU paged-path feature and
hasn't been wired into the persistent worker yet.

**Where read.**
- `crates/braidinfer-runtime/src/bin/chat.rs:46` (compat check vs.
  `MULTI_GPU`)
- `crates/braidinfer-runtime/src/model/model_load.rs:1119`

**Migration note.** Would become `--kv-quant int4` CLI arg with explicit
values (`none|int4|...`), and the compat matrix becomes a startup-time
validation in `apply_auto_modes`.

## `WEIGHT_QUANT`

**What.** Selects the weight quantization mode used to interpret /
populate the bqnt. Accepted values map to `WeightQuantMode`:

- `rnf4` → `WeightQuantMode::Rnf4` (rotated NF4, 4-bit)
- `mixed` → `WeightQuantMode::Mixed` (mixed-precision per-tensor policy)
- anything else / unset → `WeightQuantMode::Bf16` (no weight quant)

Setting this also gates whether a first-time-quantization bqnt cache is
written: caching only happens when `WEIGHT_QUANT != Bf16` and no
`BQNT_PATH` was explicitly set.

**Usage.**
```bash
MODEL=$MODEL WEIGHT_QUANT=rnf4 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** `bf16` | `rnf4` | `mixed`. Default = `bf16`. Note:
the megakernel path rejects quantized weights with the error
"Cannot use quantized weights with megakernel — use WEIGHT_QUANT=bf16
for dense models" (see `quant.rs:48`).

**Why created.** Exposes the weight-quantization mode selector for the
bqnt loader; needed because the codebase supports multiple quant schemes
that share the same on-disk container.

**Where read.**
`crates/braidinfer-runtime/src/model/model_load.rs:48`.

**Migration note.** Would become `--weight-quant {bf16,rnf4,mixed}`
CLI arg with a `model.default_weight_quant` config-file default.

## `WEIGHT_QUANT_LAYERS`

**What.** Per-layer mask restricting which transformer layers are
loaded as quantized (rest load bf16 from safetensors). Format is a
comma-separated list of integers or `start-end` ranges, e.g.
`0-11,20-31`. When set, prints a banner listing the quantized layer
set.

**Usage.**
```bash
MODEL=$MODEL WEIGHT_QUANT=rnf4 WEIGHT_QUANT_LAYERS=0-11,20-31 \
  python3 scripts/launch-gpu.py --timeout 43200 -- \
  cargo run --release -p braidinfer-runtime --bin generate -- "Hello"
```

**Default / values.** Comma-separated integers and ranges, or unset.
Default = unset (all layers honor `WEIGHT_QUANT`).

**Why created.** Bisection tool for quantization-induced divergence.
`CLAUDE.md` documents this directly: *"Per-layer quantization control:
`WEIGHT_QUANT_LAYERS=0-11,20-31` restricts Q4 to those layers (rest
load bf16). Useful for isolating which layer diverges."* Pairs with
`scripts/bisect_quant.py` to binary-search the layer that breaks under
a given quant scheme.

**Where read.**
`crates/braidinfer-runtime/src/model/model_load.rs:255`.

**Migration note.** Would become `--quant-layers 0-11,20-31` CLI arg
intended to be used together with `--weight-quant`; the parser
(integer-or-range list) becomes a clap value parser.

## Cross-variable interactions (current guards)

The runtime enforces these compat rules at startup; they are encoded in
the binaries rather than in any central validator:

- `KV_QUANT=1` + `MULTI_GPU=1` → hard error (`chat.rs:52`). KV quant
  only works on the single-GPU paged path.
- `KV_QUANT=1` + `PERSISTENT=1` → hard error (KV quant not wired into
  the persistent worker).
- `WEIGHT_QUANT != bf16` on the megakernel path → hard error from
  `quant.rs:48`.
- `MODEL=*.bqnt` → forces `BQNT_PATH` to that path (cli.rs:108-112).
- Auto: `MULTI_GPU` auto-on when bqnt > 0.85 × single-GPU VRAM and
  GPU count > 1.
- Auto: `PERSISTENT` auto-on when `MULTI_GPU` is on or the model is
  non-MoE.

A proper CLI migration should collapse these into a single
`validate_config(&RuntimeArgs) -> Result<RuntimeConfig, _>` entry
point rather than the current scattered guards.
